# 開発時言語化ツール 要求定義

> **この文書の位置づけ**
> 「何が満たされれば良いか」のみを記述する。実現手段（設計）は含めない。
> 手段を書きたくなったら、それは設計文書に属する。
>
> **記述ルール:** 手段を表す動詞を使わない。「〜すること」の形で書く。
> 例: ✕「無音で区切る」 ○「発話が欠落しないこと」
>
> **判定基準:** 「これを否定したら利用者は困るか」で判断する。
> 別の手段でも困らないなら、それは要求ではなく設計である。

---

## 1. 背景

開発中に考えを言語化したい。キーボードで書くと思考が止まるが、声に出すだけなら止まらない。
その発話をテキストとして残し、最終的に LLM に渡して要約・整理させたい。

発話は思いつきベースであり、話の筋道が通っていないことが多い。言い間違いや長い沈黙も含まれる。

本ツールでは、読みやすい文章に整えることよりも、発話者の思考過程を損なわずに残すことを優先する。

---

## 2. 利用者と利用状況

- 利用者は開発者本人ひとり。他者との共有は想定しない
- 開発マシンの前に座り、作業しながら断続的に話す
- 一回の発話セッションは数分程度
- 話す内容には技術的な固有名詞が多く含まれる

---

## 3. 要求

### 3.1 出力の正確さ

- **R-1** 発話者の意図や意味を推測して補完・修正されることなく、発話内容がテキストとして残ること
- **R-2** 言い間違い、言い直し、口ごもりが、発話されたまま残ること
- **R-3** 文章として整形されないこと。読みやすさのための修正が加えられないこと
- **R-4** 話の筋道が通っていない断片的な発話でも、内容が損なわれないこと
- **R-5** 1回の発話セッションに含まれる発話が、発話途中の区切りによって欠落しないこと

> **R-1〜R-5 の根拠:** テキストの読み手は人間ではなく LLM である。
> 言い直しや口ごもり、断片的な発話そのものが思考の情報であり、
> 読みやすさを優先して除去・修正すると LLM が判断材料を失う。

### 3.2 発話の取りこぼし

- **R-6** 開始操作の直後に話し始めても、冒頭が失われないこと

### 3.3 沈黙

- **R-7** 発話に沈黙が含まれていたことが、テキストから分かること

> 沈黙の長短を区別する要求はない。有無が分かれば足りる。

### 3.4 確認

- **R-8** 話している間、文字起こしの結果を随時確認できること

> **R-8 の根拠:** 発話中に結果を確認できることで、認識結果と実際の発話内容との
> 差異にその場で気づける。常時利用される機能であり、一時的な検証手段ではない。

### 3.5 開始と終了

- **R-9** 単純な操作で開始できること。設定を行っていない状態でも利用を開始できること
- **R-10** 明示的な操作で終了できること。時間経過や無音によって意図せず終了しないこと

### 3.6 記録の保全

- **R-11** セッション終了時に、結果がファイルとして残ること
- **R-12** 処理の途中で異常が発生した場合でも、異常発生時点までに取得された発話内容が失われないこと

> **R-12 の根拠:** 数分間の思考は再現できない。処理中の異常によって取得済みの発話が
> 失われるなら、ツールとして継続的に利用できない。信頼性が利用可否の条件そのものになっている。

### 3.7 記録の参照

- **R-13** 後から記録を読み返せること
- **R-14** 各記録について、そのセッションが行われた日時を確認できること

### 3.8 責務の範囲

- **R-15** 音声からテキストへの変換までを担うこと。要約・整形・翻訳などは含まないこと
- **R-16** 得られたテキストを、利用者が外部の LLM への入力として利用できること

### 3.9 実行環境

- **R-17** 開発マシン（Mac）上で動作すること
- **R-18** ターミナルから利用できること

### 3.10 データの取り扱い

- **R-19** 音声およびテキストについて、外部への送信の有無、送信先、および送信されるデータの種類を利用者が確認できること

> LLM に渡す時点での外部送信は許容される。ただしそれは利用者が選んで渡すもの。
> 変換処理そのものによる外部送信については、利用者が送信の有無と内容を把握できることを求める。

### 3.11 設定

- **R-20** 利用者が変更した動作設定が、次回以降の利用にも引き継がれること
- **R-21** 設定内容を、利用者が直接読み書きできる形式で確認・編集できること

> **根拠:** 毎回同じ指定を求められることは利用の障壁になる。
> また、設定内容が利用者から見えない形で保持されると、現在の動作の理由を追えなくなる。
>
> **注:** 何を設定可能とするかは設計で決まる。ここでは、設定可能な項目が存在する場合に
> それが保持され、かつ利用者から可視であることを求める。
> 保存形式・保存場所は設計に委ねる。

### 3.12 動作状態

- **R-22** 利用中、ツールが動作していることが利用者に分かること

> **根拠:** 本ツールは長い沈黙を挟みながら利用される。
> 何も表示されない状態が、正常な待機なのか、処理の停止なのかを区別できないと、
> 発話を続けてよいかの判断ができない。
>
> R-8（結果の確認）とは別の要求である。R-8 は結果が得られたときの話であり、
> R-22 は結果がまだ得られていないときの話。

---

## 4. 要求としないもの

意図的に含めないもの。後から蒸し返さないために記録する。

| 項目                                           | 理由                                                                           |
| ---------------------------------------------- | ------------------------------------------------------------------------------ |
| 複数話者の区別                                 | 一人での利用のみを想定                                                         |
| 要約・整理                                     | 外部の LLM の役割（R-15）                                                      |
| 翻訳                                           | 用途に含まれない                                                               |
| 他者との共有                                   | 個人利用のみ                                                                   |
| 開発マシン以外での動作                         | 用途が開発中に限定される                                                       |
| 認識精度の改善手段（語彙登録・後処理補正など） | 推測の持ち込みは R-1 に反する。復元は下流の LLM の役割（5.1 で検証のうえ判断） |

> ここには、要求と別の軸にある事項のみを記載する。
> 要求の裏返し（「〜しないこと」を要求している事項の再掲）は記載しない。二重管理を避けるため。

---

## 5. 未確定・要検証

要求として確定していない、あるいは検証を要する事項。

### 5.1 固有名詞の認識精度 — 決着済み（2026-08-14）

**検証結果:** 実発話（36 秒、faster-whisper small）で、日本語として自然に成立する
誤認識を確認した。

| 誤認識         | 原文        | 判定                                                    |
| -------------- | ----------- | ------------------------------------------------------- |
| `文字を越し`   | 文字起こし  | 動詞句として読めるため、下流の LLM も誤りと判別できない |
| `カラトコード` | Claude Code | 意味不明語のため、文脈から復元可能                      |

いずれも本プロジェクトの中核語彙であり、低頻度の偶発的な誤りではない。

**判断:** 追加の要求は設けない。

認識精度を上げる手段（語彙登録、認識時への語彙注入、後処理による補正）はいずれも
「実際にはこう言ったはずだ」という推測を持ち込むものであり、R-1 と相容れない。
また、管理対象が増える点でも採らない。

誤認識の復元は、テキストを受け取る LLM 側の役割とする（R-15 の責務分担に沿う）。

### 5.2 出力の正確さと随時確認の関係

随時確認できること（R-8）を満たすには発話中に結果を得る必要があり、
そのために発話を途中で区切ると、断片的な発話の認識精度が落ちる可能性がある。
すなわち R-8 は R-1・R-4 と衝突しうる。

R-5（区切りによって欠落しないこと）とは別の問題である。
R-5 は「失われないこと」を求めており、区切ること自体は禁じていない。

要求としては両方を維持する。トレードオフが生じる場合は設計段階で検討し、
必要であれば要求に立ち返る。

### 5.3 文字起こし結果の表示遅延

発話してから文字起こし結果を確認できるまでの遅延が、利用上許容できる範囲かは未検証。

**検証方法:** 実際の発話を行い、発話から文字起こし結果の確認までに生じる遅延を確認する。

### 5.4 セッション時間

通常の発話セッションは数分程度を想定しているが、想定する最大セッション時間は未確定。

最大セッション時間によって、記録の保全や文字起こし結果の確認に必要な条件が変わる可能性がある。

**検証方法:** 実際の利用を想定した発話時間を確認し、通常時と長時間利用時の差を確認する。

### 5.5 言い直し・口ごもりの保持（R-2）

第 1 段階の検証音声には明確な口ごもり（「えーっと」等）が含まれていなかったため、
R-2 は未検証のまま残っている。

言い直しの接続については保持が確認された。

**検証方法:** 口ごもりを意図的に含む発話で検証する。

### 5.6 沈黙の記録に関する判明事項（R-7）

第 1 段階の検証で、音声認識エンジンに内蔵された無音除去機能により、
沈黙の情報が文字起こし処理に到達しない事象を確認した。

これは設定値の問題ではなく、処理の構成に起因する。
無音の情報を認識処理の外側で保持する構成が必要となる。

要求 R-7 の変更は不要。設計上の制約として記録する。

### 5.7 発話の欠落経路（R-5）

第2段階の検証で、発話が出力に現れないまま失われる経路が2つ確認された。
いずれも欠落したこと自体が出力から判別できない。

- 発話区間の検出漏れ（採用部と破棄部の音量差が、実測で 5.3dB / 26.8dB と録音条件により大きく変動）
- 認識処理内部の閾値による区間の破棄

R-5 の変更は不要。設計上の制約として記録する。
完全な回避が困難な場合、欠落の発生を出力から判別できるようにすることを次善とする。

### 5.8 R-12 の限界と、対処しない判断（2026-08-16）

第3段階の検証で、R-12 の充足範囲に限界があることが判明した。

発話は「終了後の一定時間の無音」が確認されてから文字起こしされるため、
それまでの発話はメモリ上にのみ存在する。
実測で、未書き出しとなりうる長さは最長 40 秒（読み上げ音声の場合）。

明示的な終了操作は保護されているが、異常終了時には話している最中の発話が失われる。
マイク入力では音声が残らないため復元できない。

**判断: 現時点では対処しない。**

- 音声入力中の異常終了は発生頻度が低いと見込まれる
- 利用者自身による終了操作であれば、失われても問題とならない
- 失われる範囲は「話している最中の分」に限られ、再度話すことで回復できる
- 対処（音声の並行保存）は常時メモリを消費するため、得られる保護に見合わない

R-12 の変更は不要。必要が生じた場合に再検討する。
