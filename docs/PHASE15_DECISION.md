# Phase 15: Chrome拡張・ブラウザUIの撤退判断

作成日: 2026-08-07

## この文書について

Phase 5系〜Phase 10.5 にかけて実装した **ブラウザUI と Chrome拡張機能を廃止し、
CLIクライアントに集約する**という判断の記録である。

実装したものを削除する判断は、コードからは読み取れない。
なぜ作り、なぜ使わなくなったのかを残すために本書を書く。

実装そのものは削除後も参照できる（後述の[実装を参照するには](#実装を参照するには)）。

---

## 背景

| Phase          | 内容                                                               |
| -------------- | ------------------------------------------------------------------ |
| Phase 5系      | ブラウザUI（マイク / 動画ファイル / タブ共有の3モード）            |
| Phase 6.2〜6.3 | Chrome拡張機能化（`chrome.tabCapture` によるタブ音声キャプチャ）   |
| Phase 10〜10.5 | UI刷新、Zenモード、上級者向け機能の出し分け                        |
| Phase 11       | ブラウザ版のレスポンシブ対応                                       |
| Phase 14       | Raspberry Pi 4 へのデプロイ対応（ARM64 Dockerfile / 専用 compose） |

開発は一貫して Mac 上（`Dockerfile` + `docker-compose.yml`）で行っていた。
Phase 14 で初めて実機（Raspberry Pi 4 / 8GB）へ載せた結果、
**リアルタイムUIが前提としていた処理速度が実機では出ない**ことが判明した。

## 判断

**ブラウザUI・Chrome拡張機能を廃止し、CLIクライアントのみのリポジトリへ移行する。**

判断の根拠は次の3点。

### 1. 実機の処理速度が設計前提を満たさない（実測）

Raspberry Pi 4 上の実ログ（2026-08-07 06:06〜06:09、2セッション）:

```text
06:07:01 文字起こし完了（16.94秒） / 06:07:17 完了（15.54秒） / 06:07:34 完了（17.31秒）
06:08:26 完了（14.32秒） / 06:08:54 完了（12.59秒） / 06:09:13 完了（16.22秒）
```

**1回の文字起こしに 10.9〜17.3秒**（15〜21秒分の音声に対して）。
クライアントは3秒ごとに音声チャンクを送る設計のため、処理が追いつかず遅延が累積する。

滞留の証拠として、チャンク5〜9が同一ミリ秒（`06:07:01,710`〜`714`）にまとめて受信されている。
これは文字起こし処理中に受信バッファへ溜まったものを一気に読んだことを示す。

### 2. ハードウェア側に高速化の余地がない

Raspberry Pi 4 は **ARMv8.0-A / Cortex-A72** であり、以下の制約がある
（`README.md` の「注意事項（ハマりポイント）」に記載）:

- **int8 演算に非対応** — `WHISPER_COMPUTE_TYPE=int8` はエラーになるため、
  最も遅い `float32` を使わざるを得ない
- **torch は `==2.0.1` 固定が必須** — 2.1以降は ARMv8.2 以降向けにコンパイルされており、
  Cortex-A72 では SIGILL クラッシュが発生する

モデルサイズ別の実測目安も `tiny` で約14秒、`base` で約28秒であり、
**最小モデルにしても3秒チャンクには到底届かない**。
量子化・モデル縮小・スレッド調整のいずれも打ち手として成立しなかった。

### 3. リアルタイムUIとの相性が構造的に悪い

ブラウザUI・拡張機能は「話した端から画面に文字が出る」体験を前提に設計している。
15秒以上遅れる環境では、この前提自体が成立しない。

一方 CLI クライアントはバッチ的な使い方が自然で、遅延が許容される。
さらに CLI には終了待ちのタイムアウト処理がそもそも存在せず、
サーバーが何秒かかっても `session_end` を待ち続けるため、後述の問題4が発生しない。

## 撤退の過程で発見した設計上の問題

### 問題A: バッファ設定の相互依存が明文化されておらず、テキストが欠落した

`docker-compose.pi.yml` に以下の設定を置いていた:

```yaml
- CUMULATIVE_MAX_AUDIO_SECONDS=6.0 # バッファ上限6秒
- CUMULATIVE_TRANSCRIPTION_INTERVAL=5 # 5チャンク(=15秒)ごとに文字起こし
```

しかしトリミングは**文字起こし後にしか実行されない**設計（Phase 7.0 で意図的にそうした）のため、
バッファ長は構造上「3秒 × 5チャンク = 15秒」以上になる。**6.0秒は原理的に達成不可能だった。**

結果、トリミング判定が毎回真になり、毎回トリミングと強制確定が走って
`last_confirmed_segment_end` の整合が壊れた:

```text
1回目: 音声前半を文字起こし  → 確定 83文字, last_end=15.0s
2回目: 音声後半（前半とは異なる発話）を文字起こし
       → 確定 83文字のまま、暫定 0文字   ← 一段落ぶんがまるごと破棄された
```

トリミングでバッファ先頭が切り詰められると次回のWhisperタイムスタンプは0から振り直されるのに、
`last_confirmed_segment_end` は 15.0s のまま引き継がれ、
新しいセグメントが「すでに確定済み」と誤判定されて捨てられていた。

**対応済み**: `CUMULATIVE_MAX_AUDIO_SECONDS=20.0` に修正。
併せて `README.md` の「ハマりポイント」と `app/config.py` のコメントに
`3秒 × CUMULATIVE_TRANSCRIPTION_INTERVAL` より大きくすべき制約を明記した。

### 問題B: 終了ハンドシェイクがクライアント側タイムアウトに依存していた

クライアント（拡張・ブラウザUI共通）が「完了状態」へ遷移する経路は3つしかなかった:

1. `session_end` 受信
2. `summary_result` 受信
3. タイムアウト満了（要約OFFで20秒 / ONで120秒）

**`ws.onclose` は完了状態へ遷移させない**設計だった。
そのためサーバーの最終処理が20秒を超えると、次の順序で不整合が起きる:

```text
06:07:17,265 chunk=12 受信
INFO: connection closed          ← クライアントが20秒タイマーで先に切断
06:07:34,589 ✅ セッション終了     ← その17秒後にサーバーが最終処理を完了
06:07:34,590 🔌 WebSocket接続切断
```

サーバーが送る `session_end` は既に閉じた接続へ送られる。
`WebSocketManager.send_json` は未接続時に例外を投げず `False` を返すだけなので、
サーバー側は成功したように見え、クライアントは「処理中」のまま取り残される。

**未対応（意図的）**: 理由は次節。

## 見送った修正とその理由

| 対象                                         | 見送った理由                                                                                                                      |
| -------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Pi 4 の処理速度                              | ハード制約。設定では3秒未満に到達不可能。チャンク間隔の延長かハード変更が必要                                                     |
| `ws.onclose` で完了状態へ遷移                | 拡張・ブラウザUIの JavaScript 固有。廃止対象のため                                                                                |
| `stop()` の例外保護（try/catch）             | 同上                                                                                                                              |
| 20秒固定タイムアウトの動的化                 | 同上。CLI はタイムアウト処理を持たないため移行で自動的に解消                                                                      |
| `finalize` 例外時の `session_end` 未送信     | サーバー側だが、実ログでは `🏁 累積バッファセッション終了` が毎回出ており、この経路は発火していなかった。今回の症状の原因ではない |
| 要約処理のイベントループブロック             | 要約機能をOFFで運用しているため実害なし（`async def` 内で同期 `requests.post` を呼んでいる問題は残存）                            |
| `SessionManager.delete_session()` 未呼び出し | セッション辞書が30分残るのみ。今回の症状と無関係                                                                                  |

### 「直さない」を選んだ理由

問題B（終了ハンドシェイク）は、タイムアウト延長や `onclose` 対応で塞ぐことができ、
修正は JavaScript のみで Mac の開発環境だけで完結する。技術的な障壁はなかった。

それでも見送ったのは、**これらが対症療法にすぎないため**である。
UIが「処理中で固まる」現象は消えるが、15秒の遅延という根本は残り、
確定前のテキストが取りこぼされる問題も解決しない。

使用していない機能に対して、症状を隠すだけの修正を入れるコストは正当化できないと判断した。
根治は原因1（処理速度）側にあり、それはハード制約で解決できない。
したがって機能ごと撤退する方が筋が通る。

## 学び

- **デプロイ先の実機性能は早期に確認すべきだった。**
  Phase 14 まで Mac のみで開発したため、リアルタイムUIという設計判断が
  実機で成立しないことに最終段階まで気付けなかった。
  性能要件がある場合、最初に実機で最小構成を測るべきだった。

- **設定値の相互依存は明文化しないと必ず壊れる。**
  `CUMULATIVE_MAX_AUDIO_SECONDS` と `CUMULATIVE_TRANSCRIPTION_INTERVAL` の間には
  「前者 > 3秒 × 後者」という制約があったが、どこにも書かれていなかった。
  結果として原理的に達成不可能な値が設定され、テキスト欠落として表面化した。

- **終了処理をクライアント側のタイムアウトに依存させる設計は脆い。**
  サーバーの処理時間が想定を超えた瞬間に破綻する。
  接続のクローズ自体を状態遷移の引き金にしておくべきだった。

- **対症療法と根治のどちらを選ぶかは、その機能を使い続けるかで決まる。**
  同じ修正でも、使い続ける機能なら入れる価値があり、撤退する機能なら無駄になる。
  バグの重大さだけでなく、機能の将来を含めて判断する必要がある。

## 続編: ローカル実行への一本化（2026-08-08）

UI を廃止して CLI に集約したあと、CLI の要件を改めて整理した結果
**「発話してから画面に表示されるまで数秒以内」**と定まった。

### Pi 4 では要件を満たせないことが確定した

UI 廃止の理由と同じ制約がそのまま残っていた。CLI にしても
文字起こしに 10.9〜17.3秒かかる事実は変わらず、リアルタイム比がほぼ 1.0 で
処理が追いつかない。int8 非対応・torch 2.0.1 固定というハード制約があり、
最小の tiny モデルでも約14秒で、設定による打ち手は残っていなかった。

**そのため Raspberry Pi 対応を削除し、実行環境をローカルに一本化した。**

- `Dockerfile.arm64`、`docker-compose.pi.yml` を削除
- `docs/PHASE14_PLAN.md`（Piデプロイ計画）を `docs/archive/` へ移動

### ローカル実行での実測とチューニング

同じ音声で設定を変えて計測した結果:

| 設定                                         | 遅延           | 遅延の累積 | 精度   |
| -------------------------------------------- | -------------- | ---------- | ------ |
| small / INTERVAL=3 / チャンク3秒（変更前）   | 5.0〜5.5秒     | しない     | 高     |
| small / INTERVAL=1 / チャンク3秒             | 4.2→7.2秒      | **する**   | 高     |
| base / INTERVAL=1 / チャンク3秒              | 1.3〜1.9秒     | しない     | **低** |
| **small / INTERVAL=1 / チャンク5秒（採用）** | **3.7〜4.6秒** | しない     | 高     |

**Whisper は30秒単位でパディングするため、処理対象の音声を短くしても
処理時間はほとんど減らない**（9秒分でも18秒分でも small は3〜4秒台）。
`CUMULATIVE_MAX_AUDIO_SECONDS` を削っても遅延は縮まらず、
遅延に効くのは**モデルサイズとチャンク間隔だけ**だった。

チャンク3秒（INTERVAL=1）で遅延が累積したのはこのためで、
3秒間隔に対して処理が3〜4秒かかり、1回あたり0.5〜1秒ずつ積み上がっていた。
チャンク長を5秒にして「処理時間 < チャンク間隔」を満たすことで解消した。

base モデルは遅延が最も小さいが、固有名詞と数字が崩れるため採用しなかった。

- 「すこやかに」→「スクイアカ」
- 「シャボン玉石鹸」→「お温玉石圏」
- 「0120005595」→「01,2,00,0,5,59,5」

### 機能の絞り込み

CLI の用途を文字起こしに専念させる判断をした。
ひらがな正規化・翻訳・要約は**CLI から提供しない**（サーバー側の実装は残置）。

- ひらがなは CLI 利用者に求められていない
- 翻訳・要約もリアルタイム文字起こしという目的から外れる

### この段階での学び

- **「リアルタイム」は定義しないと設計判断ができない。**
  許容遅延を数秒と定めて初めて、Pi 4 が使えないことと、
  どの設定を動かすべきかが確定した。UI を廃止した時点で
  この整理をしていれば、CLI 移行の判断はもっと早くできた。

- **ボトルネックの性質を測らずに設定を動かすと逆効果になる。**
  更新間隔を詰める（INTERVAL=3→1）だけでは遅延が悪化した。
  処理時間がチャンク間隔を超えると累積するという構造を
  実測で把握して初めて、正しい方向（チャンク長を伸ばす）が見えた。
