## 3. 今回のタスク

タスク A・B を先に行うこと。**タスク D はその結果に依存する。**

### タスク A: 動作状態の可視化（R-22）

**R-22** 利用中、ツールが動作していることが利用者に分かること

本ツールは長い沈黙を挟みながら使われる。
何も表示されない状態が「正常な待機」なのか「処理の停止」なのかを
利用者が区別できる必要がある。

第3段階でハングが実際に発生した経緯があり、この区別には実用上の意味がある。

**制約:**

- R-8（結果の確認）を妨げないこと。表示が結果を押し流さないこと
- 発話内容そのものと、状態表示が混同されないこと

実現方法は設計に委ねる。ただし**採用した方法と、その選定理由を報告すること。**

### タスク B: 暫定値の確定（R-7, R-5）

現在、以下が暫定値のままコードに埋まっている。

| 値                 | 現在の設定 | 関係する要求 |
| ------------------ | ---------- | ------------ |
| 沈黙マーカーの記法 | `...`      | R-7          |
| 沈黙とみなす閾値   | 1.5 秒     | R-7          |
| 発話終了の確定待ち | 2.0 秒     | R-1, R-12    |

**確定にあたっての判断材料:**

R-7 が求めるのは「沈黙があったと分かること」のみ。**長短の区別は要求されていない。**

出力の読み手は LLM である。記法を決める際は、
LLM が沈黙と発話内容を混同しないことを基準とすること。
人間にとっての見やすさは判断基準ではない。

**確定させ、根拠を報告すること。** 判断に迷う場合は、選択肢と論点を報告して指示を仰ぐこと。

### タスク C: `no_speech_threshold` による区間破棄への対処（R-5）

第2段階で、`generate_segments` に 30 秒窓を丸ごと飛ばす処理（`seek += segment_size; continue`）
が存在することをソースで確認している。これは R-5（発話が欠落しないこと）に反する経路である。

**外部 VAD 構成では、この閾値を緩める余地がある可能性がある。**

内蔵 VAD を使っていた頃と異なり、現在は発話区間のみを認識処理に渡している。
長い無音が渡らないため、閾値を緩めた場合の副作用が小さい可能性がある。

**ただしこれは未検証の見込みである。** 実際に緩めて、以下を確認すること。

- 破棄される区間が減るか
- 繰り返しフレーズ等の不正な出力が発生しないか（R-1 に反する）

第2段階で、無音を丸ごと渡した条件でも繰り返しフレーズは発生しなかったが、
81 秒・最長 13.63 秒の沈黙という条件下での観測に留まる。
**より長い音声で確認すること。**

副作用が確認された場合は、緩和を採用せず、事実を報告すること。

### タスク D: 設定ファイル（R-20, R-21）

**R-20** 利用者が変更した動作設定が、次回以降の利用にも引き継がれること
**R-21** 設定内容を、利用者が直接読み書きできる形式で確認・編集できること
**R-9**（後半）設定を行っていない状態でも利用を開始できること

**タスク A・B・C の後に行うこと。** 何を設定可能にするかが、それらの結果で決まるため。

**設定項目の選定基準:**

- 利用者が実際に変更したくなるものに限る
- 「設定できるようにしておけば安全」という理由で項目を増やさないこと
- 設定項目が増えるほど、R-9（単純な操作で開始できること）から遠ざかる

**現時点で候補となりうるもの**（採否は判断に委ねる）:

- モデルサイズ
- 出力先ディレクトリ
- 沈黙の閾値、確定待ちの時間

**制約:**

- 設定ファイルが存在しない状態でも動作すること（R-9）
- 保存形式・保存場所は設計に委ねる。ただし利用者が直接編集できる形式であること（R-21）

選定した項目と、**選定しなかった候補とその理由**を報告すること。

## 5. 守ってほしい原則

### 5.1 要求を勝手に弱めないこと

要求を満たせない、あるいは実現が困難だと判断した場合、
**要求を書き換えたり、実現しやすい形に読み替えたりしないこと。**

理由とともに報告すること。要求を変更するかどうかは依頼者が判断する。

### 5.2 要求にないものを追加しないこと

「あると便利そう」「一般的にはこうする」という理由での機能追加は行わない。
必要だと考える場合は、実装せずに提案として報告すること。

**本段階は特に注意を要する。** 設定ファイルは項目を無制限に増やせる構造であり、
動作状態の表示も情報を追加し続けられる。要求に照らして必要なものに絞ること。

### 5.3 事実と推論を区別すること

報告において、以下を明確に分けること。

- 実測・ソース確認・ドキュメント記載に基づく**事実**
- そこから導いた**推論**

n=1 の観測から一般性を主張しないこと。
数値を根拠に結論を出す場合、その数値がどの時間軸・どの座標系のものかを明示すること。

### 5.4 指示書の誤りは指摘すること

第3段階では、指示書の要求番号の誤りと、
「インタフェース変更が必要」という前提の誤りを指摘のうえ、
より適切な判断を行った報告があった。これは適切な対応である。

指示書に誤り・不整合がある場合、読み替えて進めず、指摘すること。

### 5.5 検証していないものを完了として報告しないこと

第3段階では、マイク経路を検証せずにコミットした結果、
実行時にハングする状態でコミットされていた（後に自己申告のうえ修正）。

**動作確認を行った項目と、行っていない項目を報告で明示すること。**
代替手段（ファイル入力での確認など）を用いた場合は、その旨を記すこと。
