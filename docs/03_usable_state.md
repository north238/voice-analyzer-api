# 作業指示書 — 第3段階: 実用可能な状態への到達

## 0. この文書の使い方

この指示書は**第3段階のみ**を対象とする。
`docs/requirements.md` の全要求（R-1〜R-21）を今回で満たす必要はない。

第4段階以降の内容は、本段階の結果を見てから決定する。
**先回りして実装しないこと。**

---

## 1. 本段階の目標

第2段階までで、ファイル入力による文字起こしと沈黙の記録が動作している。
本段階では、**実際に喋って使える状態**にする。

到達点は「マイクに向かって喋り、結果が画面に出て、ファイルに残る」こと。

---

## 2. 前段階からの引き継ぎ

### 確定事項

- 外部 VAD（Silero VAD, `faster_whisper.vad.get_speech_timestamps()`）を使用する
- 内蔵 VAD は無効（`vad_filter=False`）
- モデルは small
- 固有名詞の誤認識には対策しない（要求外として確定済み）

### 未解決の記録（本段階では対処しない）

- 発話が黙って消える経路が2つ存在する（VAD の切り出し / `no_speech_threshold`）
- 言い直しの消失事象について、機序は未特定。外部 VAD 構成では再現していないため深追いしない

---

## 3. 今回のタスク

### タスク A: 検証コードの本体への取り込み

第2段階の外部 VAD 構成を、検証用スクリプトから本体の処理に移す。
`transcribe_async()` のインタフェース変更が必要と報告されている。

**設計上の注意（後から変更が困難な箇所）:**

タスク C（リアルタイム表示）とタスク D（記録の保全）は、
後から追加すると構造の作り直しになる。**この段階で構造に織り込むこと。**

具体的には、以下が成立する構造にする。

- 発話区間が確定するたびに、結果を「表示」と「書き出し」の両方に流せる
- セッション終了を待たずに処理が進む

処理が完了してからまとめて出力する構造にはしないこと。

### タスク B: マイク入力（R-6, R-10, R-11）

ファイル入力に加えて、マイクからの入力に対応する。

**要求:**

- **R-10** 単純な操作で開始できること
- **R-11** 明示的な操作で終了できること。時間経過や無音によって意図せず終了しないこと
- **R-6** 開始操作の直後に話し始めても、冒頭が失われないこと

R-11 について補足する。**無音が続いても終了しないこと。**
本ツールの用途では長い沈黙が頻繁に発生する。無音での自動終了は要求違反である。

R-6 について、検証方法を以下に指定する。

> 開始操作を行い、即座に短い語（「あいうえお」等）を発声する。
> 出力に冒頭が含まれているかを確認する。秒数の測定は不要。含まれるか否かで判定する。

モデルのロードに時間がかかる場合、その間の音声が失われる可能性がある。
録音の開始とモデルのロードの関係に注意すること。

### タスク C: 発話中の結果表示（R-8）

**R-8** 話している間、文字起こしの結果を随時確認できること

**判明している制約:**

外部 VAD は発話区間の終了を検出してから認識を行うため、
発話中は結果が出ない。第2段階の最長ブロックは 17.95 秒だった。

この挙動が許容できるかは未検証である。**回避策を先回りして実装しないこと。**
まず現状の構成で動かし、実際の体感を報告すること。

判断は依頼者が行う。

**表示に含めるもの:**

- 認識されたテキスト
- 沈黙マーカー

上記以外の情報（音量メーター、処理時間、進捗表示など）は追加しないこと。
必要と考える場合は、実装せず提案として報告すること。

### タスク D: ファイルへの記録（R-11, R-12, R-13, R-14）

**要求:**

- **R-11** セッション終了時に、結果がファイルとして残ること
- **R-12** 処理の途中で異常が発生した場合でも、異常発生時点までに取得された発話内容が失われないこと
- **R-13** 後から記録を読み返せること
- **R-14** 各記録について、そのセッションが行われた日時を確認できること

**R-12 が最も重要である。**

数分間の思考は再現できない。異常終了によって取得済みの発話が失われるなら、
ツールとして継続的に利用できない。信頼性が利用可否の条件そのものになっている。

セッション終了時にまとめて書き出す構造では、この要求を満たせない。

**形式について:**

出力は Markdown とする。

ファイルの配置、命名、内部構造（見出しの付け方など）は設計に委ねる。
ただし R-13・R-14 を満たすこと。

## 4. やらないこと

以下は本段階の対象外。実装しないこと。

- 沈黙マーカーの記法・閾値の確定（暫定のままでよい）
- R-5 の2経路への対処（`no_speech_threshold` の調整、欠落の可視化）
- 設定ファイル（R-20, R-21）
- 認識精度の改善（要求外として確定済み）
- 言い直し消失事象の機序特定（深追いしないと決定済み）
- 表示遅延への回避策（タスク C の報告を待って判断する）

---

## 5. 守ってほしい原則

### 5.1 要求を勝手に弱めないこと

要求を満たせない、あるいは実現が困難だと判断した場合、
**要求を書き換えたり、実現しやすい形に読み替えたりしないこと。**

理由とともに報告すること。要求を変更するかどうかは依頼者が判断する。

### 5.2 要求にないものを追加しないこと

「あると便利そう」「一般的にはこうする」という理由での機能追加は行わない。
必要だと考える場合は、実装せずに提案として報告すること。

### 5.3 事実と推論を区別すること

報告において、以下を明確に分けること。

- 実測・ソース確認・ドキュメント記載に基づく**事実**
- そこから導いた**推論**

推論を事実として report しないこと。
また、n=1 の観測から一般性を主張しないこと。

前段階では、算出方法の誤りにより誤った結論が報告された事例があった。
**数値を根拠に結論を出す場合、その数値がどの時間軸・どの座標系のものかを明示すること。**

### 5.4 段階を先に進めないこと

本段階の範囲を超える実装は行わない。
次に何をすべきか提案があれば、実装せず報告すること。

## 6. 完了時に報告してほしいこと

1. 本体への取り込みで変更したインタフェースと、その理由
2. 各要求の充足状況

   | 要求        | 内容                      | 確認方法                                       |
   | ----------- | ------------------------- | ---------------------------------------------- |
   | R-6         | 冒頭が失われない          | 開始直後の発声が出力に含まれるか               |
   | R-8         | 発話中に確認できる        | 実際に喋って表示されるか                       |
   | R-10        | 単純な操作で開始          | —                                              |
   | R-11        | 無音で終了しない          | 長い沈黙を挟んでも継続するか                   |
   | R-12        | 異常時に失われない        | 処理途中で強制終了させ、それまでの内容が残るか |
   | R-13 / R-14 | 読み返せる / 日時が分かる | —                                              |

   **R-12 は実際に異常終了を発生させて確認すること。** 構造上満たせるはず、では不十分。

3. タスク C の体感報告
   - 発話区間の終了を待つ挙動が、実際に使ってみてどうだったか
   - 表示までの待ち時間の実測値
4. 実現が困難だった要求と、その理由
5. 次段階への提案（実装はしない）

---

## 7. 検証について

タスク B・C・D はマイク入力での動作確認が必要となる。
依頼者が実施する必要がある場合は、手順を明示して依頼すること。

自動テストや録音ファイルでの代替が可能な項目については、それで構わない。
ただし**代替した項目は、その旨を報告に明記すること。**
